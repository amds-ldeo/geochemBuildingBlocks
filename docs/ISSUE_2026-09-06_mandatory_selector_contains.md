# A required schema-path selector becomes a constraint no ADA record can satisfy

**2026-09-06 · internal · `tools/schema\\\_path\\\_emitter.py` + the schema-path sidecars**

When a schema path carries a selector predicate and the field is required on that side, the
emitter makes the selector's literal **compulsory**. There are **131** such constraints across
`\\\_sources`. The literals are ours, and **none of them occurs anywhere in the 2,621-record ADA
corpus** — so wherever the constrained array is present in a record, that record cannot validate.

Nothing has been changed. This describes the mechanism, the measurement, and the options.

**Read §2 if you read nothing else** — it is the chain from a TAPP row to an unsatisfiable schema.

\---

## 1\. Correcting an earlier misattribution

This was first written up as an upstream query to the TAPP library and has been withdrawn
(`tapp` @ `2725332`). That framing was wrong. The delivered `Module\\\_Core.csv` says only this about
`Analyst`:

|Metadata Item|Description|C|D|Data Type|Keyed By|
|-|-|-|-|-|-|
|Analyst|Name(s) of the analyst(s)…|N/A|Basic|Text (free)|(none)|

No `schema:contributor`, no `roleName`, and the string `analyst` does not appear. The library says
*required at analysis level, free text*. Everything else is ours.

\---

## 2\. The chain

**Step 1 — the library states requiredness.** `Analyst` is `C=N/A, D=Basic`.

**Step 2 — we choose a placement.** `docs/modules/Module\\\_Core.schemapaths.csv:14`, `Source=authored`:

```
$Dataset.schema:contributor\\\[schema:roleName='analyst'].schema:name
```

The selector `\\\[schema:roleName='analyst']` and the token inside it were written here. The library
never mentions either.

**Step 3 — the emitter makes the selector compulsory.** `tools/schema\\\_path\\\_emitter.py:461-467`:

```python
elif (skey, val) in node.required:
    key\\\_c = {"const": val}
    allof.append({"contains": {"properties": {skey: key\\\_c}, "required": \\\[skey]}})
```

Its own comment: *"a required object branch must be CONTAINED (selector key = the token/name)"*.

**Step 4 — the generated module carries both halves.**
`\\\_sources/BaseSchema/modules/core/schema.yaml:393` (generated by `build\\\_module\\\_bb.py`):

```yaml
schema:contributor:
  items:
    allOf: \\\[{if: {properties: {schema:roleName: {const: analyst}}, ...}, then: {...}}]   # (a)
  allOf: \\\[{contains: {properties: {schema:roleName: {const: analyst}}, required: \\\[...]}}] # (b)
```

**(a) is right** — it constrains an entry that is present and is silent about the rest.
**(b) is the problem** — it requires such an entry to exist.

## 5\. Why it stayed invisible

Found while validating five draft TAPPs against their own records. VNMIR, QRIS and XRD came back
clean — but only because **none of their 52 records carries `schema:contributor` at all**, so the
constraint never fired. RAMAN and XANES do carry it: 4 of 4 and 46 of 241 fail.

More broadly, the `geochemProfile` `profile/` schemas have effectively never been run against the
corpus. A sample of `adaEMPA` and `adaTEM` records fails them **40/40 and 40/40**, on
`schema:variableMeasured` and `schema:additionalType`. These constraints do not look wrong; they
are simply untested against data.

## 5a. What has changed since this was written (2026-09-13)

Two of the three things in §2 were settled the day after this was filed, in `247474a35`. The
mechanism and the corpus mismatch were not. Read this before acting on §2 or §6.

**The path in §2 Step 2 is STALE — it was wrong for a different reason and is fixed.** The sidecar
now reads

```
$Dataset.schema:contributor\\\[schema:roleName='analyst'].schema:contributor.schema:name
```

because schema.org's Role pattern puts the name on the nested Person, not on the Role. Measured at
the time: **647 of 647 ADA contributors use the nested shape; none carries a name on the Role.** So
the old path could not have matched a record even if `analyst` had been present.

**The mandatory half was KEPT, deliberately.** `247474a35` went the other way from §6 option 1: it
made requiredness reach the leaf and every hop to it, so the constraint now reads "an analyst Role
must exist, it must carry a Person, and that Person must be named." §6 option 1 is therefore a
reversal of a decision already taken, not an open choice.

**The cost was paid with sentinels.** `80f696008` added `fill\\\_nested\\\_required`, which fills absent
required properties at any depth from the schema itself. The sentinel is **`missing`** (the commit
message says "not reported"; the code does not), now in **440 example files**. The reasoning given
was that a sentinel is honest for a transcription of a published paper and would not be for a live
archive record.

**What has NOT changed, re-measured 2026-09-13:** all **nine** literals in §4 are still emitted as a
mandatory `contains`, and `roleName='analyst'` still occurs in **0** records while
`schema:contributor` is present in 578 of 2,621. §4's finding stands in full.

### Known limitation: a `contains` on an OPTIONAL array never fires (2026-09-13)

`schema:actionProcess` is required, so the sentinel pass creates it — as the smallest object its
schema accepts, `{"@type": ["schema:HowTo"]}`. But one `anyOf` branch also wants `schema:step` to
CONTAIN a member named `Data reduction`, and `schema:step` is **optional**. So:

* `fill_nested_required` fills what the schema REQUIRES — it never adds an optional array;
* `sentinel_pinned_members` fills leaves of a pinned member that EXISTS — there is no member;
* the `contains` therefore never fires, and the minimal object satisfies no branch.

Observed on EMPA and Solution-Q-ICPMS: one error each,
`{'@type': ['schema:HowTo']} is not valid under any of the given schemas`.

This is the same mechanism this issue is about, seen from the other side. §4 counts the literals a
mandatory `contains` forces into a record; this is a mandatory `contains` that cannot be satisfied
by any automatic pass, because the array it constrains is not required and so is never created.

Either the array should be required where its `contains` is (making the constraint reachable), or
the `contains` should not be emitted for an optional array (making it honest that nothing is
enforced). Both are §6 decisions, not tooling fixes.

### A trap this creates for anyone reading a green build

`build\\\_profile` now runs the same sentinel pass over `profile/` examples (2026-09-13), so a
generated example is filled with **the schema's own pinned literals** — including
`schema:step: \\\[{"schema:name": "Data reduction"}]`, which is row 7 of §4's table and occurs in **0**
records.

The examples therefore validate while the corpus still cannot. **A green `validate\\\_examples` is not
evidence that these constraints are satisfiable by real data**, and §5's warning ("these constraints
do not look wrong; they are simply untested against data") now applies more strongly, not less. The
argument for keeping the sentinels visible is that a literal which is *always* a sentinel is the
evidence that its cardinality constraint needs revisiting.

## 6\. Options

1. **Stop emitting the mandatory half.** Keep the `if/then`, drop the sibling `contains`.
Requiredness would need to be expressed where it can be satisfied — on the property, not on a
selector literal. Smallest change, and it makes the schemas describe what the data can actually
look like.
2. **Keep it and align the ADA vocabulary.** Emit `schema:roleName: analyst`, and the named
`variableMeasured` and `schema:step` entries. This is a change to the ADA writers and to 2,621
existing records.
3. **Keep it and treat these profiles as aspirational.** Then they should not be what the forms
application validates against.

The judgement to make first is what a required selector *means*. `$Dataset.schema:contributor \\\[schema:roleName='analyst'].schema:name` can be read as "the analyst's name goes here" or as "an
analyst contributor must exist". The emitter takes the second reading for every required branch.
For `dqv:hasQualityMeasurement`, pinning `dqv:isMeasurementOf` is a defensible way to say "this
specific quality measure must be reported" — so a blanket change may be wrong for that key even if
it is right for `schema:contributor`.
