# `vocab/` — controlled vocabularies

256 SKOS code lists (`skos:ConceptScheme`) in the CDIF codelist format.

They are referenced from generated schemas by **annotation** — `schema:inDefinedTermSet:
"ada:vocab/<name>"` — rather than by a hard JSON Schema `enum`. The vocabulary is therefore
discoverable and SHACL-checkable, without a value outside the list being rejected outright by the
JSON Schema layer.

## Four kinds of file

| pattern | what it is | generated by |
|---|---|---|
| `<tapp>_<field>.json` | a per-technique enumeration lifted from a workbook's allowed-values column — `empa_diffractingCrystal`, `laQicpms_collisionGasType` | `tools/build_tapp.py`, `tools/schema_path_emitter.py` |
| `adaAnalyticalParameters.json` | the master parameter scheme: one concept per parameter across every technique, keyed by its `propertyID` URI | `tools/build_parameter_codelist.py` |
| `adaInstrumentType.json`, `adaInstrumentComponentType.json` | the tokens used in `schema:instrument[schema:additionalType=…]` and `schema:hasPart[…]` selectors | `tools/build_instrument_codelist.py` |
| `componentType.json` | the `ada:componentType` file classification | `tools/apply_componentType_enums.py` — see the componentType section of `CLAUDE.md` |

`tools/convert_vocab_to_codelist.py` normalises an older DefinedTermSet-shaped file into the SKOS
codelist form.

## Conventions

**`skos:notation` is the code a schema pins; `skos:prefLabel` is the readable name.** `SEM` →
"Scanning Electron Microscope", with the code kept as an `skos:altLabel` where the two differ. The
split matters: the notation preserves the exact token the generated schema matches on, so a label can
be improved without changing what validates. It also absorbs style drift — notation keeps
`Electron source` verbatim while prefLabel reads `Electron Source`.

`skos:inScheme` is an array and `skos:notation` a plain string; the StructuredSchema harness is
strict about both.

## Two things learned the hard way

**A selector token needs a vocabulary.** The instrument tokens (`SEM`, `ICPMS`, `TEM`, …) became hard
`contains` consts in generated schemas while only one of the seven appeared in any vocabulary — a
conforming record had to carry a literal string nothing defined, and the examples validated only
because the generator emitted the same invented token it then demanded. `adaInstrumentType` exists to
close that gap.

**Derive from what is in use, not from what is on disk.** The instrument code lists are built from
each technique's *wired* sidecar plus the module sidecars, not from every file in `docs/`, which also
holds superseded revisions. Scanning everything published retired terms — `xrayLine` survived only in
EPMA v20 and SEM v17 — and double-counted every technique in the scope notes.

## Do not hand-edit

Regenerate instead:

```bash
python tools/build_instrument_codelist.py --write
python tools/build_parameter_codelist.py
python tools/check_componentType.py          # vocab / enum cache / schema / example drift
```
