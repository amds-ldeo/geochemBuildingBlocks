# `registry/` — shared catalogues

Six generated catalogues, plus a directory of code lists, shared across every TAPP (61 `tapp/`
blocks under `techniqueProfile/`). Each subdirectory has its own README; this is what they have in
common.

| directory | holds | defs |
|---|---|---|
| `targetSpeciesColumns/` | column definitions for the target-species keyed table (was `analyteColumns/`) | 223 |
| `monitoredPropertyColumns/` | column definitions for the monitored-property keyed table | 63 |
| `reportedPropertyColumns/` | column definitions for the reported-property keyed table | 1 |
| `targetMaterialColumns/` | column definitions for the target-material keyed table | 18 |
| `parameterTemplates/` | method-level parameter templates (what the procedure specifies) | 356 |
| `parameterValues/` | per-dataset parameter values (what the analysis used) | 1232 |
| `vocab/` | SKOS code lists | 456 files |

## They are catalogues, not dependencies

The `$defs` here are **inlined into each technique's generated schema, not `$ref`d** — nothing in
`_sources/` points a `$ref` at a registry `schema.yaml`. Each is declared `isTypeLibrary: true`: a
shared catalogue you can read, diff and publish, while the copy a validator enforces lives in the
technique that uses it. The vocabularies are not `$ref`d either: a schema names one by its `@id`
(`schema:inDefinedTermSet: ada:vocab/instrumentType`).

Keys are namespaced by TAPP prefix (`epma_acceleratingVoltage`) because a bare name collides across
techniques — `detectionLimit` is generated by seven. The `@id` const inside a def carries the same
identity, so a def is unambiguous however it is keyed.

## Two generators write here

| route | tools | writes |
|---|---|---|
| path-driven | `schema_path_emitter.py` via `build_pathdriven.py` | the four keyed-column catalogues (`targetSpeciesColumns`, `monitoredPropertyColumns`, `reportedPropertyColumns`, `targetMaterialColumns`), upserting on `@id` |
| legacy matrix | `build_tapp.py` / `_tapp_lib.py` | `targetSpeciesColumns`, `parameterTemplates`, `parameterValues`, `vocab/` |

They read different sources — the sidecars versus the richer annotated workbooks — so they can
disagree about the same `@id`. `python tools/registry_ownership.py` reports, per registry, which
defs the two routes agree on, which differ, and which only one route produces.

## Who reads them

- **The forms app's TAPP registry.** `ada_metadata_forms` (in the `metadata` repository) copies
  these catalogues into its Postgres `methods` database with `python manage.py sync_registries`.
  The copy is one-way, these files to the database, matched on `@id`; `--retire-absent`
  unpublishes rows whose defs were dropped here. Its deploy (`build.sh`) clones this directory but
  does not run the sync, so the database is as current as the last manual sync. These files, not
  the database, are the source of truth.
- **CI.** `check-examples.yml` treats `vocab/productType.json` as the source of the product-type
  vocabulary.
- **Tools.** `apply_componentType_enums.py`, `apply_productType_enum.py`, `check_componentType.py`,
  `check_productType.py` and `audit_building_blocks.py` read `vocab/`.

## Do not hand-edit

Everything here is generated. Fix the source — a `docs/*.schemapaths.csv` sidecar, a table in the
`tapp/` submodule, or the generator — and re-run. A hand edit is overwritten by the next
regeneration, silently.

```bash
python tools/regenerate_schema_json.py     # *Schema.json from schema.yaml
python tools/resolve_schema.py --all       # resolvedSchema.json everywhere
```

One standing gotcha: **`parameterValues` and `parameterTemplates` reformat wholesale on any
regeneration.** After regenerating a single technique, `git checkout` those two files if you only
meant to touch that technique, or the diff carries unrelated reflow.
